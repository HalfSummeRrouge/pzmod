## 1. 项目概述

### 1.1 一句话定义

一个 MOD，三个平级子系统——**营养 / 运动 / 环境**——共享一个"代谢核心"，把角色的身体做成一套真实的生理仿真：吃什么、怎么动、在什么天气里待着，共同决定他的短期状态、长期成长与疾病。

### 1.2 与原版的关系（不变的铁律）

Build 42 原生已提供：四大营养储备池（热量/碳水/蛋白/脂肪）、体重自动增减与体重 trait、基础代谢（按性别×日常/运动/睡眠）、体温系统（Thermoregulator）、锻炼规律性与肌肉酸痛（Fitness/FitnessExercise）、Fitness 经验门控（`canAddFitnessXp()`）。

本 MOD 是**调制层，不是第二套引擎**：

- 宏观燃料、体温、体重、酸痛、经验 → **读原生状态、挂原生倍率**，不重算、不接管。
- MOD 自有状态仅三类：**8 种微量营养素记账、水合池、训练恢复数据**。
- 禁止每秒 `setEndurance()/setCalories()/setWeight()` 硬写；所有干预走倍率/修饰接口（Spike 0 验证）。

### 1.3 三大子系统

| 子系统 | 核心命题 | 关键机制 |
|---|---|---|
| 营养 | 吃进去的东西决定长期健康 | 微量记账、分类降解、7 种缺乏病、饮品药效 |
| 运动 | 怎么动决定烧什么燃料、长不长本事 | 生理底物燃料切换、训练负荷、恢复与超量适应 |
| 环境 | 天气和着装决定消耗速度与急性风险 | 温度/湿度/湿身/日照、水合、急性环境事件 |

### 1.4 设计原则

1. **生理因果优先**：每个效果都能回答"因为身体发生了什么"。冲刺不消耗维生素；啤酒不能真正解渴。
2. **连续过程用池子，长期失衡用阶梯**：水分/燃料/体温是连续状态，营养缺乏病才走多日状态机。
3. **数据驱动**：燃料曲线、降解速率、饮品系数、疾病表、环境修正全部集中配置。
4. **有前兆、可逆转、有解法**：任何致命效果前必须有玩家可读的预警，且游戏经济中存在对策。
5. **先验证后实现**：Spike 0 关闭前不写业务逻辑。
6. **依赖隔离**：第三方框架（NeatUI）只出现在适配层，业务代码不直接调用。

### 1.5 里程碑

| 里程碑 | 内容 |
|---|---|

## 4. 营养子系统

### 4.1 营养素与需求

宏量读原生（4/4/9 kcal/g 换算），需求按活动档（TDEE 2000/2700/3400，见 v2 §3.2）。微量 DRI：

| 微量 | DRI/日 | 主要流失渠道 | 缺乏病 |
|---|---|---|---|
| 钠 | 2000mg | 出汗（高温/高湿/高强度显著增加）、排尿 | 电解质紊乱 |
| 钾 | 3000mg | 同上 | 电解质紊乱 |
| 钙 | 1000mg | 日固定流失 | 骨质流失 |
| 铁 | 15mg | 日流失 + 出血（受伤/月经不做） | 贫血 |
| 维 A | 900µg | 日固定 | 夜盲症 |
| 维 C | 100mg | 日固定（且食物端降解最快） | 坏血病 |
| 维 D | 15µg | 日固定；**户外日照合成回补** | 骨质流失 |
| B1 | 1.2mg | 日固定 | 脚气病 |

评分：微量 `r_i = 当日净摄入 / DRI`（钠钾扣除出汗、铁扣除出血）；宏观 `d = clamp(热量净额 / TDEE档, -1, 1)`。UI 分档：<50% 危险 / 50–80% 注意 / 80–115% 达标 / >115% 过量。

### 4.2 数据层

- **宏量读 B42 原生 `Item` 脚本字段**（calories/carbohydrates/proteins/lipids），不重录；仅允许 Config override。
- 微量表每 100g 录入（60–80 高频食物 + 分类兜底）；**饮品表**新增补水与药效字段（见 6.4）。
- 进食事件 `OnEatFood(food, character, percent)`：克数 = percent × 物品重量（Spike 0 确认重量/腐烂/含水量语义）；宏量不记账（原生已入账），微量、水合、药效写入 MOD 状态。

### 4.3 食物分类降解（保质期联动）

每份食物的微量在**进食结算时**按当前状态实时折算（不改动物品本身，只影响吃下去获得的量）。

**降解模型**：

```
保留率(营养i) = 基础曲线_i(储存年龄) × 储存方式系数_i × 食物形态系数_i
```

| 营养素 | 新鲜食物降解 | 说明 |
|---|---|---|
| 维 C | 最快：采后约 3–5 天显著下降，两周接近归零（速率进 Config） | 新鲜蔬果是主要来源，直接制造坏血病压力 |
| 维 A / B1 | 中等：周级缓慢下降 | 长时间加热另计（后续增强，本期不做烹饪损失） |
| 矿物质（钠钾钙铁） | 极慢：保质期内视为 100% | 腐烂后仍在，但伴随患病风险 |
| 宏量（碳水/脂肪/蛋白） | 稳定；腐烂后蛋白质变质（宏量可吸收但致病/减效） | 与原版腐烂食物效果叠加，不覆盖 |

**储存方式系数**：

| 方式 | 效果 |
|---|---|
| 常温 | 按基础曲线 |
| 冷藏 | 降解速率 ×0.3（数值进 Config） |
| 冷冻 | 降解**暂停**（食用前需解冻，解冻为后续增强） |
| 罐头/密封加工 | 保质期锁定内 100%；超过保质期后按慢速曲线 |
| 烹饪产物 | 以产物类型走对应曲线（Spike 0 验证 evolved recipe 输出物的年龄如何定义） |

**设计后果**（对策闭环的一部分）：放蔫的蔬菜还能填饱肚子（宏量在）但防不了坏血病；罐头提供稳定热量与矿物质但缺 VC——玩家必须经营"新鲜食物供应链"（采集/农牧/钓鱼）而不是只囤罐头。

### 4.4 营养缺乏病（7 种，M3）

沿用 v2 的 7 病模型：7 天均值 < 阈值连续 N 天 → 潜伏/轻/中/重（0–3），达标连续 M 天逐级下降；新开档 7–10 天宽限，首发约 day 10–14；并发归一化防爆。症状清单与 v2 §4.6.2 一致（坏血病/贫血/电解质紊乱/消瘦/夜盲症/脚气病/骨质流失），骨质流失 M3-MVP 不做骨折（B42 无骨折系统）。

表现形式升级：**自定义状态图标**（第 10 章），不再借原版 Sick 图标。

## 5. 运动子系统：生理底物燃料 + 恢复适应

### 5.1 燃料底物模型（Q1 决定）

动作**不配置五维扣减向量**。每秒（累加器驱动，`OnPlayerUpdate` 只读状态）产出两个信号：

- **强度 I**（0–1）：由移动状态（静息/蹲走/步行/跑步/冲刺）与瞬时动作（翻越/爬绳/挥击，折算等效秒数）决定。
- **持续时间 T**：该强度连续维持时长。

燃料分配由"强度 × 时长 × 空腹状态"查表/曲线给出比例，并最终体现为对**原生宏量池消耗速率的乘性调制**（挂点由 Spike 0 确认；若挂点不可写，则通过原生已有的运动/日常代谢档位切换 + 热量池水平影响来近似）：

| 场景 | 碳水占比 | 脂肪占比 | 蛋白占比 |
|---|---|---|---|
| 冲刺/战斗/攀爬（高强度短时） | 高 | 低 | ≈0 |
| 步行/潜行/劳作（低强度长时） | 中→随时长下降 | 中→随时长升高 | ≈0 |
| 空腹 + 碳水枯竭 | 低 | 高 | 0 |
| 长期热量亏空 + 持续高负荷 | 低 | 高 | 开始拆蛋白（近似：优先压低 lipids 储备） |

参数全部进 Config（`fuelMix` 曲线：强度轴 × 空腹轴 → 三类比例），30 天仿真里验证"空腹长跑先低血糖后掉体重"的行为。

**动作强度档（相对倍率，仅做相对关系）**：静息 1.0 / 蹲走潜行 1.4 / 步行 2.0 / 跑步 4.0 / 冲刺 7.0。瞬时动作折算等效冲刺秒数（翻越 2–4s、爬绳 4–6s、翻窗 2–3s、上下楼 1–2s×负重比、重击 1–3s）；无"跳跃"动作（PZ 不存在，沿用 v2 结论）。战斗不重复扣宏量（原生挥击已消耗），只计训练负荷与钠钾流失。

**负重修正**用负重比 `inventoryWeight/maxWeight`（×1.0/1.15/1.3/1.5），不用绝对公斤。

### 5.2 小时级能量反馈

由原生碳水/热量池水平派生连续值（0–1）：进食分钟级回补，高强度消耗快速下降。偏低 → 耐力恢复 ×0.85、上限 −10%；枯竭 → 耐力恢复冻结。与急性事件、疾病惩罚进同一归一化通道，总修正 clamp ±20%。

### 5.3 训练负荷、恢复与适应（Q6 决定）

挂接 B42 原生 `Fitness`/`FitnessExercise`（规律性 regularity、僵硬 stiffness、`reduceEndurance`），MOD 只增数据与调制：

- **训练负荷**：每个有效动作/锻炼按强度与时长累积当日负荷；负荷过高产生"微损伤"（复用/映射原生僵硬部位）。
- **恢复条件**：恢复质量 = f(睡眠时长与质量, 蛋白质满足度, 总热量, 水合, 微损伤量)。
- **蛋白合成窗口**：训练结束后的数小时窗口内（Config，默认约 4 游戏小时），蛋白满足度在成长公式中权重提高——训练后及时吃饭真的更有用。
- **超量适应**：负荷 → 恢复完成 → 该类锻炼的经验收益放大（与原生 regularity 正反馈叠加）。
- **过度训练保护**：连续 N 天高负荷而恢复不足 → 成长系数打折、疲劳加速、僵硬加重，直到补足休息；防止"肝训练"刷级。
- **空腹/亏空训练**：负荷仍累积但恢复质量与经验收益显著降低（"空腹练=白练，练完不吃=自残"）。
- 成长发放前必过 `Nutrition.canAddFitnessXp()`；Strength 权重偏蛋白/盈余，Fitness 偏碳水/有氧；零训练零成长；负向降级未经验证前只做压制收益 + 疲劳惩罚（沿用 v2 §4.4.4）。

## 6. 环境子系统：微气候、水合与饮品

### 6.1 微气候因素（Q3 决定）

复用原生体温为核心，新增三类输入，全部转化为对原生代谢/水合/钠钾的影响，不另建体温模型：

| 因素 | 数据来源（Spike 0 验证） | 生理效果 |
|---|---|---|
| 温度 | 天气/季节 + 原生体温 | >30°C 出汗增多（钠钾/水流失↑）；<5°C 寒战产热（热量消耗↑，挂代谢倍率） |
| 湿度 | 天气湿度字段 | 高湿抑制汗液蒸发 → 散热效率↓ → 出汗更多、核心温更易升高（脱水与中暑前置因素）；低湿 → 不显性失水↑ |
| 湿身/淋雨 | 淋雨状态 + 服装湿润度 | 湿衣导热：低温下显著放大热量消耗与失温风险；高温下湿身反有助蒸发散热 |
| 日照 | 户外判定 + 昼夜/天气（云量） | 户外日照累积合成维 D（Config 系数）；暴晒轻微加速脱水 |
| 风速 | **不做** | 城郊场景收益低，明确排除 |

服装隔热/透气性的深度建模不做（M2 仅用"是否湿身 + 原生体温结果"，不逐件读服装数据；列为后续增强）。

### 6.2 水合池（Q4/Q5 决定）

连续状态 `hydration ∈ [0,100]`：

- **补充**：饮水、饮品（按补水系数）、含水食物（汤/蔬果，按含水量）。
- **流失**：基础排尿/呼吸（常数）+ 出汗（强度×温度×湿度函数）；酒精与咖啡因有额外利尿项。
- **阈值效果（连续）**：

| 水合水平 | 效果 |
|---|---|
| 100–60 | 正常 |
| 60–40 | 耐力恢复下降、口渴类提示 |
| 40–20 | 耐力上限/恢复明显下降、疲劳加快 |
| <20 | 重度：强制踉跄、视野暗角，叠加高温时快速导向中暑事件 |

脱水与"低钠"分开：纯水补充大量出汗后可能**水合正常但血钠偏低** → 电解质紊乱事件（治疗靠咸食/电解质来源，不是猛灌水）。

### 6.3 急性环境事件

连续池（水合、核心体温）越过危险阈值时触发的**短时事件**，独立于 7 天营养病状态机：

| 事件 | 触发链 | 表现（有前兆、可逆） |
|---|---|---|
| 热痉挛/低钠抽搐 | 高温高湿大量出汗、钠钾严重流失 | 前兆（肌肉抽动提示音/暗角）→ 短暂硬控；删除"控制倒置"式不可读效果 |
| 中暑（热射病） | 核心体温持续超阈 + 脱水 | 强制踉跄、意识模糊视觉、必须撤离热源+补水 |
| 失温 | 低温 + 湿身 + 持续暴露 | 动作变慢、剧烈颤抖、操作精度下降；靠近火源/换干衣恢复 |
| 脱水崩溃 | 水合 <20 持续 | 见 6.2，重度表现 |

事件有持续期与冷却，解除条件明确（补水/补盐/离开环境/取暖）；与营养病共用统一惩罚归一化器。

### 6.4 饮品真实药效（Q9 决定，Spike 0 S7② 数据验证）

**B42 饮品双路径架构**（S7② 源码验证）：

| 路径 | 物品类型 | 原生触发 | 醉酒 |
|------|---------|---------|------|
| **Food 类** | `base:food`（热饮/罐装奶等） | `BodyDamage.Eat` | `if food.isAlcoholic()` → `JustDrankBooze`（仅绷带满足，饮品不触发） |
| **FluidContainer 类** | `base:normal` + `component FluidContainer`（啤酒/葡萄酒/烈酒/汽水/果汁/水） | `IsoGameCharacter.DrinkFluid` | `if fluid.alcohol > 0` → `JustDrankBoozeFluid(alcohol)` **自动触发** |

**原生字段盘点**：
- **alcohol**：仅 Fluid 的 `Properties.alcohol`（0.0–1.0），`DrinkFluid` 自动读取并触发 `INTOXICATION`
- **caffeine**：原生**无此字段**；咖啡/茶靠 Fluid `fatigueChange`（负值=减疲劳）实现提神
- **sugar**：原生**无此字段**；糖含量体现在 Fluid `Carbohydrates`，由 `DrinkFluid` 自动写入原生营养池
- **Alcoholic**（物品脚本布尔）：仅绷带用，饮品不用；`alcoholPower` 字段存在但醉酒逻辑不调用

> **关键设计决策**：喝瓶装酒时原生 `DrinkFluid` 已自动调用 `JustDrankBoozeFluid` 触发 `INTOXICATION`，**MOD 不重复触发醉酒**。MOD 的 `alcoholGrams` 仅用于：空热量记账（7 kcal/g）、训练恢复打折、MOD 侧醉酒图标判定。

**数据驱动的饮品属性表（每 100ml）**：

| 字段 | 含义 |
|---|---|
| hydrationEfficiency | 补水效率（白水=1.0） |
| diuretic | 利尿强度（酒精/咖啡因 >0，延缓后净补水可负） |
| alcoholGrams | 酒精克数（7 kcal/g 空热量，写入原生热量池但无任何微量） |
| caffeineMg | 咖啡因（mg，MOD 自建计时） |
| sugarGrams | 糖（快速回碳水，走原生） |
| category | 白水/茶饮/咖啡/汽水/果汁/啤酒/葡萄酒/烈酒/其他（兜底） |

**查表优先级（B42 Fluid 优先）**：
1. **Fluid 类型**：`item:getFluidContainer():getPrimaryFluid():getFluidTypeString()` → 查 `FLUID_BEVERAGES`（覆盖所有瓶装/罐装饮品，同一瓶可装不同流体）
2. **物品 ID**：Food 类饮品（热饮等无 FluidContainer）→ 查 `BEVERAGES`
3. **未命中**：记录 WARN 日志（fullType/name）+ 探针 `bev_unknown` 事件，返回 nil，调用方跳过。**不做关键词/分类兜底**，避免误判掩盖漏表。

默认系数（首版参考值，进 Config，仿真与实测调优）：

| 类别 | 补水 | 特殊效果 |
|---|---|---|
| 白水 | 1.0 | 基准 |
| 汽水 | ~0.85 | 高糖快补碳水；利尿轻微 |
| 果汁 | ~0.85 | 糖 + 少量维 C（按微量表） |
| 咖啡/浓茶 | ~0.9 | 咖啡因：短时抗疲劳、利尿、之后疲劳反弹（MOD 自建计时） |
| 啤酒等低度酒 | ≈0 或微负 | 酒精利尿 + **原生醉酒** + 空热量 |
| 葡萄酒/烈酒 | 负 | 净脱水更强；**原生醉酒**更重；热量更高 |
| 汤/含水食物 | 按含水量 | 同时补宏量与微量 |

**酒精效果**（复用 B42 原生醉酒机制，MOD 只做营养侧联动）：醉酒期耐力上限与动作协调下降（原生 `INTOXICATION` 驱动）、主观变暖而实际失温风险上升（低温湿身时代谢/失温判定加重）；长期频繁摄入降低训练恢复质量（恢复系数打折）。MOD 不重建醉酒状态机。

**咖啡因效果**（原生无此字段，MOD 自建）：摄入后 `caffeineUntil` 内疲劳增长减半；到期后 `caffeineReboundUntil` 内疲劳增长×1.5 反弹。

未收录饮品记录 WARN + 探针 `bev_unknown` 事件后跳过记账，不做兜底；其他饮品 mod 需补表方可适用。

## 7. 子系统耦合总览

```
                         ┌─────────────────────────┐
        天气(温/湿/雨/日照) │      环境子系统           │
                         └───┬──────────────┬───────┘
                  出汗/寒战  │              │ 日照→维D
                             ▼              ▼
   动作强度/时长 ──► 代谢核心 ◄──── 水合池（饮品药效）
   (底物燃料切换)      │
       │              ├─ 宏量池调制(碳水/脂肪/蛋白) ──► 原生体重
       │              ├─ 训练负荷/恢复(睡眠+蛋白窗口) ──► Fitness/Strength 经验
       │              └─ 微量摄入(含降解折算) ──► 7天评分
       ▼                         │                    │
 小时级能量反馈                    ▼                    ▼
                          急性环境事件(池越阈)     7种营养缺乏病(7天阶梯)
                                          │
                                          ▼
                          统一惩罚归一化 ──► 自定义状态图标/UI（NeatUI）
```

关键闭环：

1. **闷热作战**：高湿高温 → 狂出汗 → 水合↓+钠钾↓ → 先脱水（喝水可解）→ 继续则低钠抽搐（补盐）→ 体温失控中暑。
2. **罐头经济**：罐头稳定供热量/矿物质但 VC 降解为零 → 长期只吃罐头 → 坏血病；新鲜蔬果（冷藏/采集）是解。
3. **训练日**：高强度训练 → 碳水消耗+负荷累积 → 窗口内补碳水+蛋白+睡觉 → 超量恢复涨经验；空腹硬练 → 恢复债 → 过度训练。
4. **雨后赶路**：湿衣+低温 → 热量消耗放大 → 空腹时脂肪/蛋白被动用、体重下降 → 长期叠加消瘦病。
5. **啤酒误区**：拿啤酒当水 → 利尿净脱水 + 空热量 + 醉酒失温风险。

## 8. UI 与 NeatUI Framework

### 8.1 NeatUI 依赖策略（已核实）

- **标的**：NeatUI Framework [B42]，Workshop ID **3508537032**；支持 B42.0.2–42.20.x，SP/MP；纯 UI 依赖库（widgets、布局、渲染、样式/文本、滚动列表面板、B42 API 兼容助手）；2026-09 仍活跃维护。
- **定位：硬前置依赖**。`mod.info` 中 require 并声明加载顺序（NeatUI 必须先加载）。理由：轻量（~2.3MB）、活跃、SP/MP 通吃、能吸收 B42 小版本 UI/API 变动；收益大于多一个前置的成本。
- **隔离原则**：建立 `RM_UIAdapter.lua`，本 MOD 所有界面代码只调用适配层接口（面板、标签页、进度条、列表、折线绘制、角落图标宿主）；NeatUI API 只出现在适配层内。NeatUI 若某版本不兼容或停更，重写适配层即可，业务代码零改动。
- **能力边界注意**：NeatUI 是通用 UI 库，**不是 moodle 框架**；角落状态图标由我们自建（可借其渲染/布局助手），Spike 0 验证可行性与降级路径。

### 8.2 界面组成

1. **营养/代谢面板**：状态（微量+宏量+水合+能量反馈+今日运动负荷）、7 天趋势（像素折线）、健康（疾病等级、急性事件、恢复/过度训练状态、改善建议）。沿用 v2 Vanilla-Native 视觉规范（米色纸感、深棕描边、原版位图字体、色盲三重编码）。
2. **角落状态图标（自定义 buff）**：7 营养病（四阶段）+ 脱水/中暑/失温/低钠/醉酒/咖啡因/过度训练等急性或短时状态。风格对齐原版 moodle；早期疾病给模糊图标+症状体感，确诊名称在面板查看（保留沉浸感）。
3. **入口**：原版按键绑定注册（N 键可改）+ 原版健康面板整合区块。
4. **文案**：`getText()` + Translate/EN、CN；不硬编码中文。
5. **信息精度**：原版 Nutritionist trait 控制精确毫克数显示，无 trait 只看定性档。
6. NeatUI 组件产出的界面仍须满足 Vanilla-Native 视觉规范与已知限制（手柄导航不支持，如实记录）。

## 13. 验收标准

1. 三大子系统均"读原生、挂倍率"，无双重计算：体重/体温/经验的原生逻辑与 trait 门控不被破坏。
2. 燃料切换在仿真与实机中可验证：高强度烧碳水、长时低强度烧脂肪、长期亏空才动蛋白；动作不扣维生素。
3. 水合与四类急性事件形成完整因果链（有前兆、可逆、有对策），啤酒/咖啡/白水/烈酒效果差异可感知。
4. 食物降解使新鲜蔬果与罐头产生明确营养策略差异，每种营养病在游戏经济中都有可持续解（含日照产 D）。
5. 训练闭环成立：窗口内补蛋白+睡眠促进成长，空腹/过度训练受抑制；全部经验发放受原生门控约束。
6. 状态图标与面板经 NeatUI 呈现且符合 Vanilla-Native 规范；NeatUI 被适配层隔离；缺失前置时有明确提示。
7. Spike 0 全部关闭，所有"待验证"项有结论或降级方案；改 RM_Config.lua 即可平衡，无需改逻辑。
