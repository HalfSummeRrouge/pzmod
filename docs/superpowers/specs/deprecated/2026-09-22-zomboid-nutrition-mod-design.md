- 作者：用户 × Trae

## 1. 项目概述

在《僵尸毁灭工程》（Project Zomboid）中制作一个**营养仿真 MOD**。Build 42 原生营养系统已经维护热量/碳水/蛋白质/脂肪四个储备池，并按性别 × 状态（日常/运动/睡眠）驱动体重、给 Fitness 经验上闸（`Nutrition.canAddFitnessXp()`）。因此本 MOD **不做与原版平行的第二套系统**，而是定位为原生营养系统的：

> **微量营养素扩展层 + 原生代谢/成长的调制层**

- 原生负责：宏观能量池（热量/碳水/蛋白/脂肪）、体重变化与体重 trait、基础代谢与运动能耗、锻炼经验。
- MOD 负责：新增 8 种微量营养素的记账与评分、营养疾病、以倍率形式调制原生能耗/耐力/经验、营养 UI。

### 1.1 核心目标

1. **微量营养扩展**：在原生四维之外，增加无机盐（钠/钾/钙/铁，**分账记录**）与维生素（A/C/D/B1）。
2. **运动消耗调制**：不重算 g/s 消耗，而是按动作档位与负重/温度对**原生代谢速率施加倍率**；原生未覆盖的瞬时动作（翻越/爬绳等）折算为少量等效能耗。
3. **体力耐力成长**：用 7 天营养满足度调制 Fitness/Strength 经验流（先过原生 `canAddFitnessXp()` 闸），联动小时级能量池影响短期耐力。
4. **营养疾病**：长期失衡触发 7 种末日高发营养疾病，统一表驱动、阶段递进、可恢复、并发归一化。
5. **UI 展示**：营养面板 + 7 天趋势 + 疾病详情，并整合进原版健康面板；风格完全对齐原版（Vanilla-Native）。

### 1.2 设计原则

- **不与原版重复计算**：宏观能量读写原生 `Nutrition` 池；体重交给原生 `updateWeight()`；经验受 `canAddFitnessXp()` 门控。MOD 只做"调倍率、加微量"。
- **单机优先**：B42 单机本身为内嵌服务器，写操作统一走 command 封装，预留 `sendClientCommand` 多人替换路径，第一版不保证联机。
- **数据驱动**：微量食物表、MET 锚点、疾病参数、评分曲线全部集中配置，调参不动代码。
- **模块化**：数据层/记账/历史/疾病/运动调制/成长/UI 各自独立，纯函数可离线测试。
- **先验证后实现**：所有不确定的 B42 API 行为在 Spike 0 用最小原型确认，再写逻辑。

### 1.3 分期（M1 → M3）

| 里程碑 | 内容 |
|---|---|
| **Spike 0** | B42 API 验证（见第 10 节），产出 API 行为备忘 |
| **M1** | 微量记账（8 项）+ 小时级能量池 + 7 天历史 + 原生体重联动 + 营养 UI（含健康面板入口） |
| **M2** | 4 个数值型疾病：坏血病 / 贫血 / 电解质紊乱 / 消瘦 |
| **M3** | 3 个表现型疾病：夜盲症 / 脚气病 / 骨质流失（骨折相关效果待原生能力确认） |

疾病表第一版即表驱动，分期不返工。

## 3. 营养维度模型

### 3.1 营养素定义

| 大类 | 细项 | 单位 | 记账方式 | 主要作用 |
|---|---|---|---|---|
| 蛋白质 | — | g | **读原生池** `getProteins()` | 长期成长（Strength 权重高） |
| 碳水化合物 | — | g | **读原生池** `getCarbohydrates()` | 短期运动能量 |
| 脂肪 | — | g | **读原生池** `getLipids()` | 储备与体重 |
| 热量 | — | kcal | **读原生池** `getCalories()`（4/4/9 换算） | 体重与盈余判定 |
| 钠 | Na | mg | MOD 独立标量 | 电解质（出汗流失） |
| 钾 | K | mg | MOD 独立标量 | 电解质（出汗流失） |
| 钙 | Ca | mg | MOD 独立标量 | 骨质 |
| 铁 | Fe | mg | MOD 独立标量 | 造血（贫血） |
| 维生素 A | — | µg | MOD 独立标量 | 夜盲症 |
| 维生素 C | — | mg | MOD 独立标量 | 坏血病、伤口愈合 |
| 维生素 D | — | µg | MOD 独立标量 | 骨质流失 |
| 维生素 B1 | — | mg | MOD 独立标量 | 脚气病（B1 缺失） |

> **v2 修订**：钠/钾/钙/铁**第一天就拆为 4 个独立标量**——贫血、电解质紊乱、骨质流失分别依赖不同细项，合并成一个标量后"吃高钠罐头把铁钙拉满"会使三种疾病都无法判定。数据表只录 B1，故直接命名 B1，不叫"B 族"。

### 3.2 每日需求参考值（DRI / TDEE）

配置在 `Nutri_Config.lua`。

**微量（按 DRI，作为每日流失与评分分母）：**

| 营养素 | 每日参考需求 | 备注 |
|---|---|---|
| 钠 | 2000mg | 运动出汗额外流失 |
| 钾 | 3000mg | 运动出汗额外流失 |
| 钙 | 1000mg | — |
| 铁 | 15mg | — |
| 维生素 A | 900µg | — |
| 维生素 C | 100mg | 罐头长期缺乏 |
| 维生素 D | 15µg | 缺日照；需确认食物来源闭环 |
| B1 | 1.2mg | 只吃精制谷物易缺 |

**宏观：不设独立 DRI，直接用原生热量池与活动水平（TDEE）判定盈余。** 参考活动档位（用于短期耐力与成长的归一化，不写死为一个 1840kcal 的静态分母）：

| 活动档位（按当日运动量） | TDEE 参考 | 说明 |
|---|---|---|
| 低（庇护所活动） | ~2000 kcal | — |
| 中（搜刮/步行多） | ~2700 kcal | 默认档 |
| 高（战斗/长途负重） | ~3400 kcal | 由运动刺激自动归入 |

### 3.3 评分与状态阈值

- **微量满足度**：`r_i = 当日摄入_i / DRI_i`（微量无独立消耗出口，DRI 即每日流失）；钠/钾的运动额外流失从当日摄入中扣除后再算比值。
- **宏观满足度**：由原生热量净额相对当日 TDEE 档位归一化，`d ∈ [-1, +1]`（clamp）。
- **UI 状态分档（写死在 Config）**：<50% 危险（红）/ 50–80% 注意（黄）/ 80–115% 达标（绿）/ >115% 过量（黄）。颜色之外必带文字 + 图标。

## 4. 功能设计（详细）

### 4.1 食物营养数据层

#### 4.1.1 数据来源（v2 关键修订）

- **宏量直接读 B42 原生脚本物品字段**：`Item` 类（旧 `Food` 类在 B42 已重组为 `Item` + `ItemKey.Food`）自带 `calories / carbohydrates / proteins / lipids`（每 100g 基准）。**不重录**，避免与原版及其他食物 mod 漂移；只允许在配置里写 override（修正个别错误数据）。
- **MOD 数据表只录微量**（每 100g 基准，`Nutri_DataLayer.lua`）：

```lua
FoodMicros = {
    ["Base.CannedBolognese"] = { -- 罐头肉酱
        sodium    = 480,   -- mg
        potassium = 250,   -- mg
        calcium   = 40,    -- mg
        iron      = 1.2,   -- mg
        vitA      = 15,    -- µg
        vitC      = 2,     -- mg
        vitD      = 0,     -- µg
        vitB1     = 0.05,  -- mg
    },
    -- ... 其余食物
}
```

#### 4.1.2 折算规则

- 按**实际食用重量**折算。进食事件给出的是"本口占整份比例"，克数 = 比例 × 物品当前重量（Spike 0 确认重量 API 与腐烂/含水量影响）。
- 烹饪产物（evolved recipe 输出物）与饮料在 Spike 0 专项验证。
- 第一版烹饪不改变营养（VC 流失为后续增强项）。
- 未收录微量的食物走 `FallbackCategory` 类别兜底（蔬菜/肉类/罐头/谷物…）；宏量永远有原生值，不存在"无营养"。

#### 4.1.3 数据录入范围

- M1 覆盖 60–80 个高频食物的微量；宏量自动覆盖全部 B42 食物与其他食物类 mod。
- 每种疾病必须做**对策闭环审计**：在搜刮/采集/农牧渔猎经济中确认对应营养有可持续来源。重点：维生素 D（鱼/蛋来源与日照合成，见 4.6.4）。

### 4.2 摄入结算（进食）

- **事件**：`Events.OnEatFood`。
- **B41 参考签名为 `(food, character, percent)`**，`percent` 是这一口占整份的比例而非克数；B42 确切签名以 Spike 0 验证为准。

```lua
-- 伪代码：进食 → 微量当日累计；宏观由原生自动入账，不重复记
function Nutrition_OnEatFood(food, character, percent)
    local grams  = percent * ItemWeight(food)        -- Spike 0 确认取重量方式
    local micros = Micros_GetPer100g(food)           -- 查微量表/兜底
    local factor = grams / 100.0
    for k, v in pairs(micros) do
        DailyMicroIntake[k] = DailyMicroIntake[k] + v * factor
    end
    -- 宏观不记账：原生吃食物已写入 Nutrition 池
end
```

- 微量当日累计存于玩家 ModData（`Nutri.MicroToday`），每日结算入历史后清零。

### 4.3 运动消耗系统（调制原生，而非重算）

#### 4.3.1 宏观能耗：倍率挂原生

- 不维护自有 g/s 消耗表。动作档位（休息/蹲走/步行/跑步/冲刺）与负重、温度转换为乘在**原生代谢速率上的倍率**，优先挂点：
  - `Thermoregulator.Multiplier.MetabolicRateInc / MetabolicRateDec`；
  - `Metabolics` 类与 `Fitness.reduceEndurance()`（其内部已综合负重与 metabolics）。
  - 具体可写挂点由 Spike 0 确认；**禁止每秒 `setEndurance()/setCalories()` 硬写**（会与引擎每帧回写打架）。
- 动作档位与相对倍率（相对静息=1，仅做相对关系，绝对值交给原生）：

| 动作状态 | 判定（Spike 0 确认谓词） | 能耗倍率 | 钠钾流失倍率 |
|---|---|---|---|
| 休息/站立/睡眠 | 无移动 | 1.0（用原生睡眠/日常档） | 微量 |
| 蹲走/潜行 | `isCrouching()` | 1.4 | 1.2 |
| 步行 | `isWalking()` | 2.0 | 1.5 |
| 跑步 | `isRunning()` | 4.0 | 2.5 |
| 冲刺 | `isSprinting()` | 7.0 | 4.0 |

#### 4.3.2 瞬时动作：折算"等效冲刺秒数"

v2 修订：瞬时消耗不拍脑袋给绝对值（旧表翻越 30g 碳水 ≈ 冲刺 7 分钟，明显失真）。统一折算为少量等效能耗 + 对应微量流失，数值以 Config 中 `instantMET` 表表达：

| 动作 | 等效冲刺时长 | 钠钾流失 | 检测方式（Spike 0 验证） |
|---|---|---|---|
| 翻越栅栏/矮墙 | 2–4s | 微量 | hook 对应 TimedAction 的完成回调 |
| 攀爬绳索 | 4–6s | 微量 | 同上 |
| 翻窗进出 | 2–3s | 微量 | 同上 |
| 上下一层楼 | 1–2s ×负重比 | 微量 | 监听 z-level 变化，区分上下行 |
| 重击/撞门 | 1–3s（空手破门更高） | 微量 | thump / 物体破坏路径 |

> PZ **没有独立"跳跃"动作**（只有翻越），旧表"跳跃 8g"行删除。也不存在"timed action 完成"全局事件，需逐类 hook action 的 `perform/complete`。
> 碳水储备过低时翻越落地踉跄作为可选反馈保留。

#### 4.3.3 战斗消耗

原生挥击已有耐力与 Fitness 消耗，MOD **不重复扣碳水**；只做两件事：
1. 高热环境/长时间战斗的钠钾额外流失（按挥击次数 × 武器重量档，小额）。
2. 疾病系统对耐力恢复/挥击稳定性的调制（见 4.6）。

武器重量档（<1.5 / 1.5–3 / >3 kg）仅用于钠钾流失与动作时长，不再产出每击几十克碳水。

#### 4.3.4 环境修正

- **负重用负重比**而非绝对公斤：`inventoryWeight / maxWeight`，分档 ×1.0 / ×1.15 / ×1.3 / ×1.5，自动随力量与 trait 缩放。
- **温度优先复用 `Thermoregulator`**：>30°C 提高钠钾流失倍率；<5°C 提高产热（代谢倍率）。不新增与原生体温竞争的模型。
- 第一版不做湿度与风速。

#### 4.3.5 小时级能量池（短期反馈）

新增一个**连续衰减的小时级能量状态**（基于原生碳水/热量池水平派生，0–1），进食回补、运动消耗，使"吃饭→有力气"分钟级可感，替代旧设计"午夜结算后才生效"的粗粒度：

| 能量池状态 | 效果 |
|---|---|
| 充足 | 无修正 |
| 偏低 | 耐力恢复 ×0.85、上限 -10% |
| 枯竭（连续高强度且无进食） | 耐力恢复冻结（饿着跑不动） |

### 4.4 长期均值与体力耐力成长

#### 4.4.1 每日结算与 7 天滚动窗口

- 存储：ModData `Nutri.History`（最近 7 天），结构 `{day, 微量摄入向量, 宏观净额(读原生), 运动刺激}`。
- 微量每日记录摄入量（评分时除以 DRI）；宏观净额从原生热量池的日变化读取，不自行累加。
- 每日结算时机：以游戏时钟/`EveryDays` 类事件为准，**Spike 0 必须验证睡眠加速期间是否漏触发**。

#### 4.4.2 归一化

- 微量：`r_i = 摄入_i / DRI_i`（钠钾扣除出汗流失），7 天均值用于疾病与成长。
- 宏观：`d = clamp(热量净额 / 当日 TDEE 档, -1, +1)`。

#### 4.4.3 短期耐力（小时级）

由 4.3.5 能量池 + 近 2 天宏观净额共同决定，与疾病效果走统一的归一化通道（见 4.6.1）。

#### 4.4.4 长期成长（周级，调制而非平行发经验）

```
XP修正系数 = g(训练刺激, 营养满足度)
```

v2 修订：

1. **先过原生闸**：发放/放大任何 Fitness 经验前检查 `Nutrition.canAddFitnessXp()`，原生 trait 封顶逻辑保持原样，绝不绕过。
2. **修正公式过零问题**：`g(刺激, r)` 必须满足 `g(0刺激, *) = 0`（不训练不长 Fitness）、`g(刺激, 吃够=1.0) > 0`（吃够 DRI 时训练应正成长，旧公式在此为 0）。
3. **营养权重分化**：Strength 偏蛋白质/盈余；Fitness 偏碳水/有氧。
4. **低运动 + 盈余只增重、不涨 Fitness/Strength**（旧表"靠吃长体能"删除）。
5. **高运动 + 亏空**：经验降速乃至小额负增长（"练伤自己"）；负 `AddXP` 是否真正降级需 Spike 0 验证，未证实前负向效果改用"压低正向经验获取 + 疲劳/酸痛惩罚"实现。
6. 单日修正幅度 clamp 防刷；耐力类总修正 clamp ±20%；多病并发归一化。
7. 实现路径优先 hook `FitnessExercise` 的 xp/metabolics modifier；平行 `AddXP` 仅作补充并扣除与原生重叠部分。

| 运动量 | 营养状况 | 结果 |
|---|---|---|
| 高 | 盈余 | 经验快速正增长 |
| 高 | 平衡 | 稳定正增长 |
| 低 | 任意 | 不涨体能；盈余则体重交原生增加 |
| 高 | 亏空 | 负向（先压制获取，验证后再做降级） |
| 低 | 亏空 | 缓慢流失（原生代谢主导） |

### 4.5 体重联动（完全委托原生）

- MOD **不设体重速度、不设 55kg/95kg 绝对阈值**。体重读写全部经 `Nutrition.getWeight()/setWeight()` 与 `setIncWeight()/setDecWeight()/setIncWeightLot()`，变化由原生 `updateWeight()` 与 `weightGain/weightLoss`、`caloriesToGainWeight*` 驱动。MOD 只通过宏观满足度影响热量池水平。
- 体重分档直接消费原生 `applyTraitFromWeight()` 区间：

| 原生区间(kg) | 原生 trait |
|---|---|
| >100 | Obese |
| 85–100 | Overweight |
| 75–85 | Normal |
| 65–75 | Underweight |
| 50–65 | Very Underweight |
| ≤50 | Emaciated |

- 疾病"消瘦"与体重的联动以原生 trait/区间为触发条件，不自造阈值。
- **"先脂肪后肌肉"无法直接实现**（原生无身体成分模型，只有体重标量）：近似表达为亏空期 MOD 优先压低 `getLipids()` 储备、尽量保留 `getProteins()`，但不承诺成分语义。
- 原生 Fitness 经验封顶 trait 逻辑保持原样。

### 4.6 营养疾病系统

#### 4.6.1 疾病模型（统一表驱动）

- 触发：某营养素 7 天均值低于阈值**连续 N 天** → 潜伏 → 轻度 → 中度 → 重度（0–3 级）。
- 恢复：达标连续 M 天 → 逐级下降。
- **宽限期**：新开档/历史不足 7 天不触发任何疾病；首个疾病最早约 day 10–14 出现（潜伏期长、早期轻、恢复便宜），抑制"病→没法觅食→更缺"的死亡螺旋。
- 多病并发：所有属性惩罚进统一汇总器后做归一化（clamp，防属性爆负/NaN）。

#### 4.6.2 疾病清单与分期

| 疾病 | 缺失营养 | 分期 | 负面表现（0→3 递进，均可读、可预期） | 状态量 |
|---|---|---|---|---|
| 坏血病 | 维生素C | M2 | 伤口愈合 -20/-40/-60%；疲劳恢复 -10/-25/-40%；重度持续失血倾向 | `scurvy_level` |
| 贫血 | 铁 | M2 | 耐力上限 -10/-20/-35%；运动耗耐力 +15/+30/+50%；重度偶发**强制踉跄+暗角警告**（替换不可读的"0.5s 失灵"） | `anemia_level` |
| 电解质紊乱 | 钠/钾 | M2 | 耐力恢复 -20/-40/-60%；重度抽搐前**先有视觉/音效前摇**，再短暂硬控（删除"控制倒置"，与 bug 无法区分） | `electrolyte_level` |
| 消瘦 | 蛋白/热量 | M2 | 苍白外观；受伤加重 +10/+20/+35%；耐力恢复 -10/-25/-40%；重度负重上限大降。以原生体重 trait 为门槛 | `wasting_level` |
| 夜盲症 | 维生素A | M3 | 夜晚视野 -20/-40/-60%；光照半径 -20/-35/-50%。光照 API 在 Spike 0 验证，失败降级为屏幕暗角蒙层 | `nightblind_level` |
| 脚气病 | 维生素B1 | M3 | 奔跑后呼吸急促/疲劳涨幅增大；日常疲劳 +15/+30/+50%；重度步行即疲劳 | `beriberi_level` |
| 骨质流失 | 维生素D/钙 | M3 | **M3-MVP 只做**：已有伤口愈合 -30/-50/-70%、摔落/重击受伤加重。**"骨折率/骨折愈合"依赖原生并不存在的骨折系统，移入后续版本**（B42 `BodyDamage` 包无骨折类） | `osteoporosis_level` |

#### 4.6.3 症状实现原则

- **可读、可预期**：任何硬控/失控效果前必须有明确前摇（音效、暗角、角色姿态）。禁止"随机 1s 不能动 / 控制倒置 / 随机掉武器"这类无预警且与 bug 难辨的效果；武器掉落如需保留，改为"挥击变慢/颤抖"。
- **数值层**优先用倍率/修饰接口（耐力恢复、负重、受伤判定、疲劳），不与引擎每帧回写冲突。
- **视觉层**：苍白用 HumanVisual 调色（Spike 0 验证）；夜盲以光照 API 为首选、屏幕蒙层为降级。
- **不新增 Moodle 图标**（MoodleType 为 Java 枚举，扩展代价高）：借用原版 Sick/Endurance 等已有 moodle 表达，或在进入新阶段时给**低频沉浸文本提示**一次；详细诊断放进 UI。
- 输入锁定、调色、光照三项均标注"待 Spike 0，失败有降级"。

#### 4.6.4 对策闭环（强制审计）

每种病都必须在食物经济中存在可持续解。重点风险：**维生素 D**——第一版无日照合成且罐头几乎不含 D，会导致数月后全员无解患病。M1 二选一或都做：
1. 微量日照合成：户外日照时间按系数产生 D（进 Config）；
2. 明确鱼/蛋等 D 来源并核对刷新/采集产出量。

## 6. 测试策略

### 6.1 分层

| 层 | 方式 | 工具 |
|---|---|---|
| 纯函数单测 | 评分/归一化/疾病状态机/成长系数/折算 | luajit（PZ 同款 Lua 5.1 JIT） |
| 30 天虚拟人仿真 | 罐头/均衡/高运动三档画像逐日推进，验疾病节奏与热量经济 | luajit 表驱动，不进游戏 |
| 集成测试 | 沙盒 + debug 命令造境 | 游戏内 |
| 持久化 | 进食→读档→数值保持；跨 schemaVersion 合并 | console + 存档 |
| 性能 | 1 游戏小时 CPU 增量，目标**平均 <0.2ms/帧**（OnPlayerUpdate 累加器、只读状态） | 游戏内 profiler |

### 6.2 关键验证用例

1. 摄入：吃 100g 罐头豆 → 微量折算正确；宏量与原生池增量一致、不双计。
2. 调制：冲刺 30s → 原生代谢倍率正确叠加；翻越一次 → 等效能耗在量级内（不再是 30g 碳水）。
3. 能量池：连续高强度不进食 → 分钟级进入"恢复冻结"；进食后恢复。
4. 成长：7 天盈余+训练 → 正增长且受 `canAddFitnessXp()` 约束；零训练不涨 Fitness；亏空+高训练 → 负向路径符合 4.4.4。
5. 体重：盈余少动 → 原生增重并自动获得对应体重 trait；封顶 trait 仍生效。
6. 疾病：缺 VC 连续 N 天 → 潜伏→轻度；补 M 天 → 逐级恢复（含读档）；宽限期内不发病。
7. 对策闭环：每种病都能在对应食物/日照经济中恢复（含维 D）。
8. 并发：7 病全触发 → 归一化无负数/NaN；所有硬控都有前摇。
9. UI：Nutritionist 开/关的数值精度差异；健康面板整合无破坏。

### 6.3 Debug 工具（开发版内置）

- 一键喂食 / 直接设定各营养素与能量池 / 跳天（含睡眠加速模拟）/ 强制疾病阶段 / 显示每秒倍率与扣减明细 / 30 天仿真一键跑。

全部参数集中 `Nutri_Config.lua`，30 天仿真与游戏内调参结合。

## 9. 验收标准

1. MOD 不与原生宏观营养/体重重复计算：盈余/亏空经由原生池与 `updateWeight()` 体现，原生体重 trait 与 Fitness 封顶不被破坏。
2. 吃/动四组合下，分钟级（能量池）与周级（成长/体重）差异均可感知。
3. 7 种疾病按 M2/M3 均可触发、演进、恢复，效果可读可预期，并发不爆表，且每种病存在可获得的恢复途径。
4. UI 在独立面板与原版健康面板正确展示，风格与原版一致；Nutritionist trait 控制数值精度。
5. 改 `Nutri_Config.lua` 即可平衡，无需改逻辑；30 天仿真与 debug 工具可支撑调参。
6. Spike 0 清单全部关闭并有行为备忘，所有"待验证"项都有确定结论或降级方案。
